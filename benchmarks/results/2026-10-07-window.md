# Windows compute presentation continuation — 2026-10-07

The window adapter and Vulkan presentation diagnostic are implemented. The
automated lifecycle completes on both GPUs. Earlier intermittent AMD suspension
timeouts and native visual review remain open. This is not a black-hole image
or a completed Milestone 5.

## Configuration

Windows on the hardware in [the geometry report](2026-10-07.md). LLVM-MinGW
Clang 23.1.2, CMake 4.4.3, Ninja 1.13.2; warnings as errors, no fast-math.
GLFW 3.4, Vulkan-Headers 1.4.321, glslang 15.0.0 and validation/SPIRV-Tools from
Windows SDK 1.4.321.1 are pinned in THIRD_PARTY.md. The loader remains supplied
by the OS/driver. Shader target is Vulkan 1.3. No SDK installer was executed.

Presentation uses queue family 0 on both adapters, FIFO, one frame in flight,
RGBA8 compute output and an extent-preserving blit into a supported UNORM
swapchain. KHR swapchain maintenance1 presentation fences protect semaphore
reuse and swapchain destruction. These establish safe release, not evidence of
on-screen appearance; see the [Khronos fence specification](https://docs.vulkan.org/refpages/latest/refpages/source/VkSwapchainPresentFenceInfoKHR.html).

## Open failure and limits

Earlier AMD runs reach only 10–11 presented frames before entering the suspended
state until the 45-second deadline. The instrumented failure reported 10 frames,
2,165 suspended loops, **zero acquisition retries and zero validation errors**.
This was initially suspected to be an acquisition stall, but those counters
do not support that diagnosis. It also occurs with validation disabled; polling
events between short fence waits did not resolve it. A later strict run passes
without a rendering logic change or longer test deadline. Window minimization,
zero framebuffer extent and zero surface extent all suspend this renderer;
the timeout now logs minimized/framebuffer/recreation state to distinguish them
on recurrence. The cause is not isolated to application, driver, hybrid
presentation or desktop state. Do not infer that the successful run fixed it.

Native screenshot/manual UI review could not run: the Computer Use tool reported
that its native pipe was unavailable. Window submissions and compute readbacks
do not prove the desktop compositor displayed the expected colors.

Linux, forced out-of-memory/device loss/surface loss, noncoherent memory hardware,
HDR, multiple frames in flight and missing-extension hardware remain untested.
KHR maintenance1 support is mandatory for this diagnostic; no EXT-only fallback
is implemented. Unsupported devices fail explicitly. API calls may block; fence
waits are bounded to 30 seconds, acquisition to 100 ms, and the smoke loop to
45 seconds. Driver-dependent fatal teardown is not a recovery mechanism.
Sanitizers cover project host code, not shader execution or vendor binaries.

There are no FPS or throughput claims. GPU Hamiltonian RHS/step/trajectory
conformance, shadow/lensing images, radiative disk emission and the scientific
interface remain future work. CPU physics/numerical algorithms were unchanged.
A fresh CPU-only configure also succeeds with Vulkan and renderer disabled.

## Reproduce

```powershell
.\tools\bootstrap-vulkan.ps1 -Window -Validation
.\build.ps1 -Configuration Release -Window -RequireValidation
.\build.ps1 -Configuration Debug -Window -RequireValidation
.\build.ps1 -Configuration Sanitize -Window -RequireValidation
.\tools\validate-vulkan.ps1 -Window -Device 1 -Capture out\window-smoke\nvidia\final.ppm
.\tools\validate-vulkan.ps1 -Device 0
# AMD run; earlier intermittent suspended-state timeouts remain investigated:
.\tools\validate-vulkan.ps1 -Window -Device 0 -Capture out\window-smoke\amd\final.ppm
# Interactive diagnostic (Escape closes):
.\out\build\windows-clang-release\kerr_window.exe --device 1
```

Indices are local enumeration; inspect `kerr_gpu --probe` on other machines.
